02 / 14  ·  THE PROPERTY

the protocol does NOT prove claims are true — only that they were signed.

plain reading The protocol's claim is narrow on purpose: a memory set, signed under an identity, is provably part of that identity's verifiable history. Verifiability is about authorship + integrity — not epistemic truth.
03 / 14  ·  WHAT IS ALETHECH
what is alethech

definition

alethech is a Python package that provides cryptographically verifiable memory continuity for AI agents.

It lets an agent sign its memory commits with Ed25519, link them in a Merkle DAG, rotate keys without losing identity, and prove to a third party that its memory was not tampered with.

The protocol does NOT prove that the agent's claims are true — only that they were signed by the identity that claims them.

scope The unit of verification is the commit. Identity is the key. The DAG is the proof.
audience Any third party that needs to decide whether to trust an agent's reported memory: an auditor, a downstream agent, a human reviewer.

merkle dag

read the graph D dangles off C2 but sits past the cutoff — its ancestry is not proven, so it is rejected. C3 is signed under key-002 and still reaches back through the cutoff_head, so it is valid.
cutoff_head The causal frontier at the moment of key rotation — not a timestamp. It is a commit hash, not a wall-clock reading.
05 / 14  ·  HOW IT WORKS
how it works

six steps

  1. alethech init generates an Ed25519 keypair + identity derived from public key
  2. alethech commit --content memory.json signs the content + links to DAG parent
  3. alethech verify checks signatures, DAG integrity, identity binding, reachability
  4. alethech key rotate revokes old key with cutoff_head, grants new key, both signed by root
  5. alethech export --output dir/ creates portable signed bundle
  6. alethech import --input dir/ verifies bundle + writes atomically (target untouched on failure)
workflow Init once. Commit per memory delta. Verify on demand. Rotate when a key is compromised or aged out.
atomicity Import verifies the entire bundle before writing a single byte to the target store. Failure leaves the target untouched.
06 / 14  ·  EQUATIONS
the four equations

math, not magic

commit_id = sha256(JCS(object − {commit_id, signature}))

content-addressed id over the canonicalized object, with the id and signature fields removed.

signature = Ed25519_sk(JCS(object + commit_id))

deterministic Ed25519 signature over the canonical object plus its freshly computed commit_id.

agent_id = did:alethech: + b32(sha256(JCS(pk))[:16])

identity derives from the root public key — operational keys rotate, the agent_id does not.

C ∈ ancestry(cutoff_head) ⟹ VALID_HISTORICAL

a commit is valid iff its ancestry is reachable from the last pre-rotation head.

note JCS = RFC 8785 canonical JSON. Same bytes in, same hash out — every time, on every machine. Without canonicalization, two semantically-equal JSON objects could hash differently and break content addressing entirely.
07 / 14  ·  VERDICTS
the two verdicts

valid or not

verdict VALID_HISTORICAL C ∈ ancestry(cutoff_head)
verdict NOT_IN_PROVEN_PRE_ROTATION_HISTORY C ∉ ancestry(cutoff_head)
critical: the verifier does NOT claim to prove WHEN the commit was created — only that it is reachable from a verified head.
membership, not timing The verifier checks ancestry membership. It does not check wall-clock creation time. A commit proven to be in ancestry was made before the cutoff — that is the only timing claim.
08 / 14  ·  GUARANTEES
the guarantees

what it does and does not

  • ✓signature verifies against declared public key
  • ✓commit_id matches SHA-256 of canonical JSON
  • ✓agent_id derives from public key (not declared)
  • ✓key rotation preserves identity (root-bound)
  • ✓revoked key commits checked against ancestry(cutoff_head)
  • ✓checkpoint head must be ancestor of current HEAD
  • ✓import is atomic (verify-then-write, target untouched on failure)
  • ✗does NOT prove content truth
  • ✗does NOT encrypt at rest
  • ✗does NOT detect rollback without external checkpoint
  • ✗does NOT delegate permissions between agents
  • ✗does NOT call any LLM
read carefully The ✓ items are properties the verifier checks. The ✗ items are properties no signature-based verifier can check from bytes alone.
no LLM alethech is a pure cryptographic protocol. It does not infer, summarize, or judge — it signs, hashes, and verifies.
09 / 14  ·  KEY ROTATION
key rotation

rotate keys, keep identity

key-001 revoked
cutoff_head
key-002 active

agent_id derives from the root, not the operational key. Keys can be revoked and replaced; the identity they attest to does not move. Reachability through the cutoff_head is what carries continuity across the rotation.

why strike-through Revocation is permanent and visible. A struck key still exists in the DAG as a historical signer — but no post-cutoff commit signed by it is accepted.
10 / 14  ·  ANTI-ROLLBACK
anti-rollback

sequence is the authority

forward monotonic sequence — accepted:

10→ 11→ 12→ 13→ 14→ 15 [ ACCEPTED ]

stale sequence — rejected as rollback:

5 [ REJECTED — rollback ]

the system clock is NOT the authority — sequence is. Time lies; monotonic counters cannot be wound back without breaking the chain.

monotonic, not temporal The sequence is monotonic — the system clock is NOT the authority. Two commits cannot share a sequence number; the counter only moves forward.
